# 最小垂直スライス開発フロー

## 1. 目的

この文書は、0→1開発および新しいユーザー価値を追加する機能開発において、必要な既存・新規レイヤーを通じて利用可能な機能を完成させる「最小垂直スライス」を開発単位とし、仕様作成から最終検証までの標準サイクルを定める。

このサイクルでは、実装前の最小TDDを実装の道筋とガードレールとして使用する。網羅性は実装前TDDへ求めず、実装後にコードと処理フローを調査して、単体・コンポーネント・統合・E2Eテストを補完する。

## 2. 基本原則

1. **新機能を機能単位で完成させる**  
   0→1開発や新機能追加では、フロントエンド全体を先に作り、その後でバックエンド全体を作るような大規模な水平分割を通常の開発単位にしない。

2. **変更ファイル数ではなく、価値の完結性で垂直性を判断する**  
   垂直スライスは、毎回すべてのレイヤーを変更することを意味しない。既存のAPI、サービス、ドメイン、永続化をそのまま利用してユーザー価値が完成するなら、フロントエンドだけのコード変更でも垂直スライスとして扱う。関係のないレイヤーへ形式的な変更を加えない。

3. **実装前TDDは最小に保つ**  
   承認済み仕様の中心的な振る舞い、重大反例、必要な代表回帰だけを事前テストとして選ぶ。

4. **実装後に検証範囲を広げる**  
   実装したコードの分岐、境界値、エラー処理、状態遷移、レイヤー間の接続を調査し、不足するテストを追加する。

5. **実装を仕様の根拠にしない**  
   実装後に未カバー分岐を見つけても、その分岐の期待結果をコードから決めない。仕様から一意に導けなければ仕様不足として人間へ戻す。

6. **1スライスを検証まで完了してから次へ進む**  
   実装だけを終えて別機能へ移らない。実装後テスト、全体回帰、記録、人間による完了確認までを1サイクルとする。

## 3. 最小垂直スライスの定義

最小垂直スライスは、次の条件を満たす最小の機能単位である。

- ユーザーまたは外部利用者にとって独立した価値がある
- 入力から最終的な出力または永続状態まで観測できる
- 単独で仕様と受け入れ条件を記述できる
- 他のスライスと分離して実装・検証・リリースできる
- 1回の開発サイクルで完成可能な大きさである

ここでいう垂直性は「コード変更が複数レイヤーに存在すること」ではなく、「ユーザー価値を提供する実行経路が、既存部分を含めて必要な終点まで接続されていること」を指す。

| 変更例 | 判定 |
|---|---|
| 既存APIを利用して新しい一覧・可視化画面を追加する | Frontendだけのコード変更でも、利用可能な機能として完成すれば垂直スライス |
| 既存データを使うクライアント側の検索・並べ替えを追加する | Frontendだけで価値が完結する垂直スライス |
| 新規登録フォームを作るが、必要なAPIへ接続せずmockのまま終える | 未完成の水平スライス |
| 新APIを実装するが、利用予定の画面やクライアントへ接続しない | 明示されたAPI単体提供が目的でない限り、未完成の水平スライス |
| 表示崩れやアクセシビリティ不具合を修正する | 局所変更。垂直スライスを強制しない |
| 外部挙動を変えない内部リファクタリング | 局所変更。垂直スライスを強制しない |

例えば「購入物管理」を一度に実装するのではなく、次のように分割する。

- 購入物を1件登録し、一覧へ反映する
- 登録済み購入物を編集する
- 登録済み購入物を削除する
- 在庫と消費速度から購入予定日を表示する

「購入登録フォームだけ」の変更でも、既存APIへ接続して登録が完了し、結果をユーザーが確認できるなら完成した垂直スライスである。必要なAPIが存在しないのに、画面をmockやハードコードへ接続した状態で終える場合は未完成となる。「DynamoDBの登録処理だけ」も、独立したAPIや内部基盤の提供自体が明示された目的でない限り、通常は完成した垂直スライスではない。

### 局所変更

次の変更では、垂直スライスを強制せず、影響範囲内で独立して検証可能な最小変更を単位とする。

- 外部挙動を変えないリファクタリング
- フロントエンドまたはバックエンド内で完結する不具合修正
- UI、アクセシビリティ、表示だけの改善
- パフォーマンス改善
- テスト追加
- 依存関係更新
- CI、インフラ、ドキュメントなどの保守
- 後続スライスに必要な技術的前提作業

局所変更では、関係のないレイヤーのコードやテストを形式的に追加しない。変更の影響がレイヤー境界を越える場合だけ、必要な統合テストやE2Eを追加する。垂直スライスを適用しない場合は、その理由と観測可能な完了条件を仕様または変更記録へ記載する。

## 5. 開発サイクル

### Phase 0: Baseline

AIは変更前に、関連するテスト、Lint、型チェック、ビルドの状態を確認する。

- 既存失敗と今回の変更による失敗を区別する
- 使用可能なテスト基盤と未整備の基盤を確認する
- 既存実装へのretrofitでは、現状の挙動を証拠として記録する
- Baselineのコマンドと結果をテスト計画へ記録する

Baselineが失敗している場合は、対象機能のTDDへ進む前に、修正するか既存問題として分離するかを人間と決める。

### Phase 1: 垂直スライス仕様

人間とAIが、機能単位の仕様を共同作成する。

仕様には少なくとも次を含める。

- 機能の目的とユーザー価値
- スライスの開始点と終了点
- ユーザーから観測可能な振る舞い
- 対象となるレイヤーと外部境界
- 正常時と失敗時の状態
- 対象外
- 受け入れ条件
- Blocking / Important / Deferredに分類した確認事項

Blockingな確認事項をすべて解消し、人間が承認した時点でSpecification Gateを通過する。

### Phase 2: 実装前の最小TDD

AIは承認済み仕様から論理テストケースを作成し、最小TDD原則に従って事前テストを選ぶ。

原則として含めるものは次のとおり。

- 変更目的を直接表すテスト
- 重大リスクがある場合の重大反例
- 壊れやすい既存契約がある場合の代表回帰

人間がテスト計画を承認した後、AIがテストコードを作成する。新しい振る舞いは、実装前に意図した理由で失敗するValid Redを確認する。

事前TDDの目的は、すべての分岐や境界値を網羅することではない。実装の進路を定め、危険な逸脱を防ぐことである。

### Phase 3: 垂直スライス実装

AIは、仕様の振る舞いを成立させるために必要なレイヤーを実装し、既存レイヤーを含む処理経路を利用可能な機能として完成させる。既存APIなどで価値が完結する場合、変更対象が1レイヤーだけでもよい。

典型的な対象は次のとおり。

- UIとユーザー操作
- フロントエンドの状態管理と入力検証
- APIクライアントとAPI契約
- HTTPルーターと入出力スキーマ
- ユースケースとドメインロジック
- 永続化モデルと外部サービス接続

スライス内部では、小さなRed-Green-Refactorを複数回行ってよい。ただし、途中のレイヤーだけを完成扱いにして次の機能へ移らない。

実装中に仕様不足や仕様との矛盾が判明した場合は実装を停止し、仕様・論理テストケース・テスト計画を更新して人間の再承認を得る。

承認済みの最小TDDテストがGreenになり、リファクタ後も維持された時点でTDD Greenを記録する。この時点では、まだスライス全体のテスト完了とはみなさない。

### Phase 4: 実装後テスト分析

AIは実装全体を読み、line coverageとbranch coverageを取得して、未検証箇所を調査する。

確認対象は次のとおり。

- 未実行の条件分岐
- 境界値
- エラー処理
- 状態遷移
- 時刻、乱数、UUID
- 永続化前後の整合性
- 認証・認可・ユーザー分離
- レイヤー間の変換と契約
- 実装中に判明した新しいリスク

未カバー箇所を次に分類する。

| 分類 | 扱い |
|---|---|
| Critical | 必ずテストを追加する |
| Important | 原則追加する。追加しない場合は理由を記録する |
| Low risk | カバレッジ率だけを目的に追加しなくてよい |
| Unreachable / Generated | 除外理由を記録する |
| Specification gap | 期待結果を決めず、仕様確認へ戻る |

カバレッジ率は、未検証箇所を発見する指標として使用する。数値を上げるためだけに価値の低いテストを追加しない。

### Phase 5: 単体・コンポーネントテストの補完

TDDテストだけでは不足する小さな契約を、最も低コストで正確に検証できるレベルへ追加する。

- Domain: 計算、境界値、不変条件、状態遷移
- Services: ユースケース、失敗時の副作用、外部境界との調整
- Models: シリアライズ、キー、条件付き更新、永続化変換
- Frontend components/hooks: 入力、表示、操作、loading/error状態

同じ契約を複数レベルで無意味に重複検証しない。

### Phase 6: 統合テスト

AIは、実装した処理フローとレイヤー間の契約を実際につないで検証する。

主な対象は次のとおり。

- FastAPIリクエストからサービス、DynamoDB Local、レスポンスまで
- 認証情報からユーザー識別、データアクセス制御まで
- APIスキーマと生成されたフロントエンド型の整合
- 外部サービスアダプターの入出力とエラー変換
- 失敗時に不正な永続化や副作用が発生しないこと

統合テストは内部関数の呼び出し順ではなく、境界を越えた結果と状態を検証する。

### Phase 7: E2E

AIは、ブラウザから永続化・画面反映までの代表的なユーザーフローをE2Eで検証する。

E2Eには原則として次を含める。

- スライスの価値を最も直接的に示す代表正常系
- ブラウザからしか確認できない重要な失敗経路
- 認証やユーザー境界など、全体接続でのみ保証できる重大反例

全境界値や全バリデーションをE2Eへ重複させない。それらは単体・コンポーネント・統合テストへ置く。

### Phase 8: 全体検証と完了判定

AIは次を実行し、結果を実装後テストレポートへ記録する。

- 対象テスト
- 全単体・コンポーネントテスト
- 全統合テスト
- E2E
- Backend / FrontendのLintとformat check
- 型チェック
- Frontend build
- 必要なインフラ静的検証

失敗した検証をskip、削除、期待値の緩和によって通過させない。環境上実行できない検証がある場合は、未実行の内容、理由、影響、後続対応を明示する。

人間が仕様、テスト内容、実行結果、残存リスクを確認した時点でSlice Complete Gateを通過する。

## 6. テストレベルの選択

| 検証対象 | 優先するテスト |
|---|---|
| 計算、ビジネスルール、不変条件 | 単体テスト |
| UIの入力、表示、状態 | コンポーネントテスト |
| DynamoDBの実際の読み書き | DynamoDB Localを使う統合テスト |
| HTTP契約と永続化の接続 | API統合テスト |
| 外部サービスとの変換 | adapter/contract統合テスト |
| ユーザー操作から最終状態まで | 少数のE2E |

テストは、対象の欠陥を最も速く、決定的に、原因を特定しやすいレベルへ置く。

## 7. 完了条件

1つの最小垂直スライスは、次をすべて満たしたときに完了する。

- [ ] 機能仕様と論理テストケースを人間が承認している
- [ ] Blockingな仕様不足が残っていない
- [ ] 最小TDDテストでValid Redまたは正当なRed例外を確認している
- [ ] 変更したレイヤー数にかかわらず、仕様で定めた開始点から最終的な出力・状態まで機能が成立している
- [ ] 承認済みのTDDテストがGreenである
- [ ] 実装後にline / branch coverageと処理フローを確認している
- [ ] Criticalな未カバー箇所が残っていない
- [ ] Importantな未カバー箇所をテストしたか、残す理由を記録している
- [ ] 必要な単体・コンポーネント・統合・E2Eテストを追加している
- [ ] 全テスト、Lint、型チェック、ビルドが成功している
- [ ] 未実行の検証と残存リスクを記録している
- [ ] 人間がスライスの完了を確認している

## 8. 人間とAIの責務

### 人間

- 機能の目的、要求、制約を提示する
- AIと仕様を共同作成し、最終承認する
- 最小TDDテスト計画を確認・承認する
- 実装後の追加テストと残存リスクを確認する
- Slice Completeを最終判断する

### AI

- 最小垂直スライスの候補と分割理由を提示する
- 仕様不足を分類し、必要な確認事項を提示する
- 最小TDDテストを作成し、Valid Redを確認する
- スライスに必要な全レイヤーを実装する
- カバレッジと処理フローを調査し、実装後テストを追加する
- 統合テストとE2Eを実装・実行する
- 全検証結果と残存リスクを記録する
- 仕様にない期待結果を独断で確定しない

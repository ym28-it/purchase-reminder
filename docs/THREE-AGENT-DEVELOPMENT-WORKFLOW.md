# 3エージェント開発運用

## 1. 目的

この文書は、仕様・テスト・実装の責務を分離し、AIが自らの実装を通すためにテストや期待結果を調整することを防ぐため、次の3エージェントによる開発運用を定める。

1. 契約オーナー・レビューエージェント
2. テストエージェント
3. 実装エージェント

人間は、プロダクト上の判断と各承認ゲートを担当する。自動化の対象は、承認済みTDD計画を入力とするテスト作成、実装、実装後テストまでを基本とする。

この分離は欠陥を完全に防ぐものではない。論理テストケースを期待動作の唯一の真実として共有し、エージェントごとの変更権限、成果物、停止条件を制限することで、確認バイアスと責務の混同を減らす。

## 2. 適用範囲

この運用は、[最小垂直スライス開発フロー](./VERTICAL-SLICE-DEVELOPMENT-WORKFLOW.md)に従う機能開発を主な対象とする。

局所的なドキュメント修正、依存関係更新、単純なリファクタリングなどで3エージェント分離のコストが変更リスクを上回る場合は、適用しない理由と代替するレビュー方法を記録して省略できる。

初期運用では、会話内のオーケストレーターが各エージェントを順番に起動する。専用CLI、GitHub Actions、自動マージはこの文書の対象外とし、実運用で安定した手順だけを後から自動化する。

## 3. 基本原則

### 3.1 論理テストケースを期待動作の唯一の真実とする

期待結果は `docs/specs/<feature-slug>-test-cases.md` でのみ定義する。

TDD計画、実テスト、実装後テストレポートはTest Case IDで論理テストケースを参照し、期待結果を独自に追加・変更しない。

期待結果の変更が必要な場合は、仕様と論理テストケースへ戻り、人間の再承認を得る。

### 3.2 エージェント間を自然言語だけで引き継がない

各工程は、承認済み文書、コミットSHA、テスト結果、状態コードを介して引き継ぐ。

前工程のエージェントによる要約は補助情報であり、後工程の判断根拠にはしない。

### 3.3 次工程への遷移を担当エージェント自身に決めさせない

テストエージェントは実装エージェントへ直接実装開始を指示しない。実装エージェントも実装後テストの開始や完了を自己承認しない。

次工程への遷移は、オーケストレーターが成果物と機械的条件を検査して決める。仕様上の判断が必要な場合は自動遷移せず、契約オーナーと人間へ戻す。

### 3.4 テストをコミット単位で凍結する

Valid Red確認後のTDDテストをテスト専用コミットとして固定する。実装エージェントは、そのコミット以降にテストを変更しない。

テストの修正が必要な場合は実装を停止し、変更理由を契約オーナーへ返す。

### 3.5 自動マージしない

自動工程の完了は「レビュー可能な状態」を意味する。契約オーナーと人間による最終レビュー前にマージしない。

## 4. 登場主体

| 主体 | 主な責務 | 自動工程への関与 |
|---|---|---|
| 人間 | 要求、プロダクト判断、各ゲート承認、Slice Complete判断 | 開始指示と例外判断 |
| 契約オーナー・レビューエージェント | 仕様、論理テストケース、TDD計画、最終レビュー | 前後を担当。自動工程中はコードを書かない |
| テストエージェント | TDDテスト、Valid Red、実装後テスト、テストレポート | 自動工程の前半と後半 |
| 実装エージェント | 凍結済みテストを満たすプロダクトコード | 自動工程の中央 |
| オーケストレーター | 状態遷移、権限検査、コマンド結果確認 | 制御のみ。第4の判断エージェントではない |

オーケストレーターは、会話内のルートエージェントまたは将来の状態機械が担う制御機能である。仕様やテストの意味を決定する独立した第4エージェントとして扱わない。

## 5. 自動工程の開始条件

人間が「TDD開始」を指示しても、次をすべて満たさない場合、オーケストレーターはテストコード作成を開始しない。

- [ ] 仕様がSpecification Gateを通過している
- [ ] 論理テストケースがLogical Test Case Gateを通過している
- [ ] TDD計画に論理テストケースの参照コミットSHAがある
- [ ] 中心的契約がCore Contract Gateを通過している
- [ ] 最小TDDテストセットがTest Plan Gateを通過している
- [ ] 対象ブランチと基準コミットSHAが指定されている
- [ ] 未解決のBlockingな仕様不足がない
- [ ] 各エージェントの変更可能範囲が定義されている

論理テストケース承認直後に自動化を開始したい場合は、まず契約オーナーが中心的契約とTDD計画を作成し、人間の承認を得る。承認を自動化工程の途中へ含める場合は、Core Contract GateとTest Plan Gateで必ず一時停止する。

初期運用では、人間の介入を開始時と終了時に限定するため、Test Plan Gate通過後を自動工程の開始点とする。

## 6. 全体フロー

### Stage 0: 契約準備

契約オーナーと人間が、次を作成・承認する。

- 機能仕様
- 論理テストケース
- 中心的契約
- 最小TDDテストセット
- TDD計画

ここまでは自動オーケストレーションの対象外とする。

### Stage 1: TDDテスト作成

オーケストレーターがテストエージェントを起動する。

テストエージェントはBaselineを確認し、承認済みTDD計画のTest Case IDを実テストへ変換してValid Redを記録する。プロダクトコードは変更しない。

成果物:

- Baseline記録
- TDDテストコード
- Test Case IDと実テストの対応
- Red実行結果
- テスト専用コミット

推奨コミット:

```text
test: add approved <feature> TDD tests
```

### Stage 2: Automated Red Gate

オーケストレーターは次を検査する。

- プロダクトコードが変更されていない
- 承認済みTest Case IDが実テストへ対応している
- 実テストからTest Case IDへ追跡できる
- Baselineと今回のRedが区別されている
- 失敗が環境、fixture、import、mock設定の不備ではない
- Red例外がTDD計画と一致する
- テスト専用コミットが存在する

条件を満たさなければ停止し、実装エージェントを起動しない。

通過時は、TDDテストの対象パスとハッシュ、テスト専用コミットSHAを凍結記録として保存する。

### Stage 3: 垂直スライス実装

オーケストレーターが、凍結済みテストと承認済み文書を入力として実装エージェントを起動する。

実装エージェントは、仕様で定めた開始点から最終状態までが成立するプロダクトコードを実装する。テストを変更せず、承認済みTDDテストをGreenにする。

成果物:

- プロダクトコード
- 必要なリファクタリング
- TDDテストのGreen結果
- 実装専用コミット

推奨コミット:

```text
feat: implement <feature> vertical slice
```

### Stage 4: Automated Green Gate

オーケストレーターは次を検査する。

- 凍結済みTDDテストが変更されていない
- 承認済みTDDテストがGreenである
- テストの削除、skip、assertion緩和がない
- 実装エージェントが許可外ファイルを変更していない
- 関連するLint、型チェック、ビルドが成功している
- 実装専用コミットが存在する

条件を満たさなければ、状態に応じて停止または制限付き再試行とする。

### Stage 5: 実装後テスト

オーケストレーターは、実装時の会話コンテキストを引き継がない新しいテストエージェント実行を開始する。

テストエージェントは、次を入力として実装後テストを行う。

- 承認済み仕様
- 論理テストケースと参照コミットSHA
- TDD計画
- テスト専用コミットSHA
- 実装専用コミットSHA
- 実装されたコード

実施内容:

- TDD候補外Test Case IDの引き継ぎ
- 実装と処理フローの分析
- line coverageとbranch coverageの確認
- 不足する単体・コンポーネントテスト
- 統合テスト
- E2E
- 全Test Case IDの消化確認
- 実装後テストレポート作成
- テスト・レポート専用コミット作成

推奨コミット:

```text
test: complete <feature> post-implementation verification
```

### Stage 6: Automated Completion Check

オーケストレーターは次を検査する。

- 全論理Test Case IDに検証先または対象外理由がある
- Criticalな未カバー箇所が残っていない
- Importantな未対応に理由がある
- 必要な単体、コンポーネント、統合、E2Eが実行されている
- 全テスト、Lint、型チェック、ビルドが成功している
- 仕様と論理テストケースが無断変更されていない
- 実装後テストレポートが存在する
- 未実行項目と残存リスクが記録されている
- TDDテスト、実装、実装後テストがコミット上で区別できる

通過後、状態を `REVIEW_READY` として契約オーナーへ返す。自動マージしない。

### Stage 7: 契約レビューと人間承認

契約オーナーは、エージェントの完了報告だけに依存せず、次を直接確認する。

- 仕様と実装差分
- 論理Test Case IDと実テストの対応
- Red、Green、全体回帰の実行証跡
- テスト凍結後の変更有無
- 実装後テストとカバレッジ分析
- 対象外理由と残存リスク
- 変更コミットの責務分離

契約オーナーがレビュー結果を提示し、人間がSlice Completeを最終判断する。

## 7. 各エージェントの責務と禁止事項

### 7.1 契約オーナー・レビューエージェント

#### 責務

- 人間と機能要求を整理する
- 垂直スライスの範囲を定義する
- 仕様と論理テストケースを作成する
- 中心的契約候補と最小TDDテストセットを整理する
- 人間による承認を記録する
- 自動工程への入力を固定する
- 完了後に仕様、実装、テストを独立してレビューする
- 仕様不足、実装欠陥、テスト欠陥を分類する
- Slice Completeの判断材料を人間へ提示する

#### 禁止事項

- 同一スライスの自動工程中に、テストまたはプロダクトコードを実装する
- 実装エージェントの説明だけを根拠に承認する
- 実装結果に合わせて仕様や論理テストケースを緩和する
- Blockingな仕様不足を独断で補完する
- レビュー指摘を自ら修正して、そのまま自己承認する
- 人間の承認が必要なゲートを代理承認する

契約オーナーがレビューで修正の必要を発見した場合は、該当エージェントへ戻し、修正後に再レビューする。

### 7.2 テストエージェント

#### 責務

- 承認済み仕様、論理テストケース、TDD計画を入力として使用する
- Baselineを実行・記録する
- 承認済みTDDテストを実装する
- Valid Redまたは承認済みRed例外を確認する
- Test Case IDと実テストの追跡関係を維持する
- 実装後にコードと処理フローを分析する
- 不足する単体、コンポーネント、統合、E2Eを追加する
- 実装後テストレポートを作成する
- 実装欠陥と仕様不足を状態コードで報告する

#### 許可する変更

- テストコード
- fixture、fake、stub、test helper
- テスト専用設定
- TDD計画のBaseline、Red、Green実行記録
- 実装後テストレポート
- テスト実行に必要な範囲のテスト基盤

#### 禁止事項

- プロダクトコードを変更する
- 仕様、論理テストケース、中心的契約、承認済み期待結果を変更する
- 実装を通すためにassertionを削除または緩和する
- テストを削除、skip、xfail化して成功扱いにする
- 内部実装を過剰にmockし、対象処理を迂回する
- 未承認の期待結果を追加する
- 環境不備やfixture不備をValid Redとして扱う
- テスト本数やカバレッジ率だけを目的に価値のないテストを追加する
- 自らの成果物を承認し、実装エージェントへ直接開始を指示する
- 実装欠陥を見つけた際にプロダクトコードを修正する

テスト容易性のためにプロダクトコード変更が必要な場合は、`BLOCKED_TESTABILITY`として停止し、必要な変更と理由を報告する。

### 7.3 実装エージェント

#### 責務

- 承認済み仕様、論理テストケース、TDD計画、凍結済みテストを入力として使用する
- 最小垂直スライスとしてユーザー価値を完成させる
- 承認済みTDDテストをGreenにする
- 必要なプロダクトコードとリファクタリングを実施する
- 仕様不足、テスト欠陥、実装上の阻害要因を状態コードで報告する
- 変更内容と実行結果を記録する

#### 許可する変更

- プロダクトコード
- スキーマ、migration、生成コードなど、仕様実現に必要な成果物
- 実装に必要な設定
- 実装内容を説明する技術文書。ただし仕様や期待結果は変更しない

#### 禁止事項

- 凍結済みTDDテストを変更する
- 実装後テストを先回りして作成する
- テストを削除、skip、xfail化する
- assertionや期待値を実装結果に合わせて変更する
- 仕様、論理テストケース、中心的契約、TDD計画を変更する
- 未確定仕様を独断で実装へ固定する
- Test Case IDの対応を変更する
- 特定テストデータだけを通すハードコードを行う
- 失敗を握りつぶしてGreenとして報告する
- 自らの実装をSlice Completeとして承認する

テストが誤っていると判断した場合は変更せず、`BLOCKED_TEST`として根拠を報告する。仕様が不足している場合は `BLOCKED_SPEC` として停止する。

## 8. オーケストレーターの責務と禁止事項

### 責務

- 開始条件を検査する
- 各エージェントへ必要最小限の入力を渡す
- エージェントを直列に起動する
- 状態、コミットSHA、テストハッシュ、実行結果を保存する
- 各自動ゲートの機械的条件を検査する
- 許可外ファイルの変更を検出する
- 再試行回数を制限する
- 停止状態を契約オーナーへ返す
- `REVIEW_READY`で契約オーナーへ引き渡す

### 禁止事項

- 仕様や期待結果の意味を決定する
- 人間の承認を代替する
- テストまたはプロダクトコードを修正する
- エージェントの自己申告だけで次工程へ進める
- 失敗した検証をskipして先へ進める
- 無制限にエージェント間を往復させる
- 仕様不足を通常の実装失敗として再試行する
- 自動でPRをマージする

## 9. 状態と停止条件

### 状態

| 状態 | 意味 |
|---|---|
| `READY` | 開始条件を満たしている |
| `TESTING_RED` | TDDテスト作成中 |
| `RED_VALIDATED` | Automated Red Gate通過 |
| `IMPLEMENTING` | プロダクトコード実装中 |
| `TDD_GREEN` | Automated Green Gate通過 |
| `POST_TESTING` | 実装後テスト中 |
| `REVIEW_READY` | 契約オーナーによるレビュー待ち |
| `BLOCKED_SPEC` | 仕様判断が必要 |
| `BLOCKED_TEST` | TDDテストの妥当性判断が必要 |
| `BLOCKED_TESTABILITY` | テスト容易性のための設計判断が必要 |
| `INVALID_RED` | Redが未実装契約の不成立を示していない |
| `IMPLEMENTATION_FAILED` | 承認済みTDDテストをGreenにできない |
| `IMPLEMENTATION_DEFECT` | 実装後テストでプロダクトコードの欠陥を検出 |
| `ENVIRONMENT_FAILURE` | 環境または外部依存により検証不能 |

### 停止ルール

次の場合は自動工程を停止し、契約オーナーへ返す。

- 仕様または期待結果の判断が必要
- 仕様・論理テストケース・TDD計画が無断変更された
- テスト凍結後にテスト差分がある
- エージェントが許可外ファイルを変更した
- Redが環境やテスト基盤の不備による
- テストと実装のどちらが誤っているか機械的に判断できない
- 実装後テストで新しい外部契約が必要になった
- CIまたは開発環境が再現不能
- 許可した再試行回数を超えた

初期運用では、`INVALID_RED`と`IMPLEMENTATION_FAILED`に限り、同じ責務範囲で最大1回だけ再試行できる。それ以外は自動修正ループへ入れない。

## 10. 変更境界

| 主体 | テスト | プロダクトコード | 仕様・論理テスト | TDD計画 | 実装後レポート |
|---|---:|---:|---:|---:|---:|
| 契約オーナー | 変更しない | 変更しない | 作成・更新 | 設計・承認記録 | レビュー |
| テストエージェント | 変更可 | 変更禁止 | 変更禁止 | 実行記録のみ | 作成・更新 |
| 実装エージェント | 変更禁止 | 変更可 | 変更禁止 | 変更禁止 | 変更禁止 |
| オーケストレーター | 変更禁止 | 変更禁止 | 変更禁止 | 変更禁止 | 変更禁止 |

例外的な変更が必要な場合は、作業を継続せず、理由と必要な変更を契約オーナーへ返す。

## 11. コミットと証跡

最低限、次のコミット境界を維持する。

1. TDDテストとValid Red
2. プロダクトコードとTDD Green
3. 実装後テストとレポート

各工程は次を記録する。

- 入力文書とコミットSHA
- 担当エージェントの役割
- 変更ファイル
- 実行コマンド
- 結果
- 未実行項目
- 状態コード
- 次工程へ渡すコミットSHA

テスト凍結後の変更は、ファイルハッシュまたはテスト専用コミットとの差分で検出する。

## 12. 契約オーナーの最終レビュー

契約オーナーは、少なくとも次を確認する。

- [ ] 仕様と論理テストケースが無断変更されていない
- [ ] 承認済みTDD計画と実テストが対応している
- [ ] Valid Redが未実装契約の不成立を示している
- [ ] テスト専用コミット後にTDDテストが変更されていない
- [ ] 実装が仕様の開始点から終了点まで成立している
- [ ] 実装エージェントがテストを変更していない
- [ ] 実装後テストが処理フローと未カバー箇所を検証している
- [ ] 全Test Case IDに検証先または対象外理由がある
- [ ] 対象外理由と残存リスクが妥当である
- [ ] 全テスト、Lint、型チェック、ビルドの証跡がある
- [ ] 変更コミットが責務ごとに分離されている
- [ ] 自動工程の停止・再試行履歴が記録されている

レビューで欠陥を見つけた場合、契約オーナー自身が修正せず、責務に対応するエージェントへ差し戻す。

## 13. 初期導入方針

最初の垂直スライスでは、専用のオーケストレーターコードを作らず、会話内のルートエージェントがこの文書に従って直列実行する。

初回の目的は、次を観測することである。

- 引き継ぎに不足する入力
- 機械的に判定できるゲート
- 人間または契約オーナーへ戻す必要がある判断
- 各エージェントの変更境界が現実的か
- Red、Green、実装後テストのコミット分離が機能するか
- 再試行が必要になる典型的な失敗

初回の結果をレビューした後、安定した状態遷移と検査だけをCLIまたはCIへ移す。認証、永続状態、並列実行、自動マージを最初から実装しない。

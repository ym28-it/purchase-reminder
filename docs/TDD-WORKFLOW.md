# TDDワークフロー（仕様確定 → テストケース → 中心的契約 → テスト → 実装）

プロジェクト非依存の汎用テンプレート。新しいリポジトリで使うときは、このファイルをそのまま
コピーし、プロジェクト側のCLAUDE.mdから参照する（あるいはこのファイル自体を配置して
参照リンクを張る）。プロジェクト固有のディレクトリ構成・層構造・担当分担などは、この
ファイルではなくプロジェクト側のCLAUDE.mdに書く。

## 目的

「実装を先に書いてから、それに合わせて仕様書とテストを後付けする」進め方は、実装のバグや
未定義動作がそのまま「仕様」として固定されてしまう。これを避けるため、**期待される振る舞い
を実装コードから独立して言語化し、それをID付きで文書化してからテスト・実装に進む**、という
手順を徹底する。

## この文書のスコープ

この文書は、垂直スライス開発サイクルのうち、仕様確定から実装前の最小TDD、最小実装がGreenになるまでを扱う。TDD Greenは機能全体のテスト完了を意味しない。以後は [最小垂直スライス開発フロー](./VERTICAL-SLICE-DEVELOPMENT-WORKFLOW.md) に戻り、実装後の単体・コンポーネント・統合・E2Eテストと全体検証を行う。

## 適用する判断基準と成果物

テストの選定・品質・最小性の判断には、[最小TDDにおけるテスト作成原則](./MINIMUM-TDD-TEST-PRINCIPLES.md)を必ず適用する。このワークフローは実行手順を、原則書はテスト判断の基準を担う。

各変更では、論理テストケースの承認後に [中心的契約選定フロー](./CORE-CONTRACT-SELECTION.md) を適用する。[中心的契約選定テンプレート](./templates/core-contract-selection.md)を `docs/specs/<feature-slug>-core-contracts.md` として保存し、AIの候補抽出と人間の承認を記録する。

Core Contract Gate通過後、[最小TDDテスト計画テンプレート](./templates/minimum-tdd-test-plan.md)をコピーして、仕様ファイルと同じ `docs/specs/` に `<feature-slug>-test-plan.md` として保存する。承認済み中心的契約、仕様不足、承認、Baseline・Red・Green・Regressionの証跡をこのファイルへ記録する。

## 運用ゲート

1. **Specification Gate**: Blockingな仕様不足がなく、人間が仕様Markdownを承認している
2. **Logical Test Case Gate**: 仕様とのトレーサビリティを持つ論理テストケースを人間が承認している
3. **Core Contract Gate**: AIが候補と対応テストケースを整理し、人間が中心的契約を承認している
4. **Test Plan Gate**: AIが承認済み中心的契約から作成した最小テストセットを人間が承認している
5. **Red Gate**: 実装変更前に、対象テストが意図した理由で失敗することを確認・記録している
6. **TDD Green Gate**: 承認済みの最小TDDテストを緩和せず通し、リファクタ後もGreenを維持している

Characterization Test、既存テストによる保護、純粋なリファクタリングではRed Gateを省略できるが、原則書に定める例外理由をテスト計画へ記録する。

テスト追加前に既存のテスト・Lint・型チェックを実行してBaselineを記録する。既存失敗と今回のRedを混同せず、環境不備やfixture不備による失敗をValid Redとして扱わない。

## 全体像

```
① 仕様をMarkdownで記録（機能ごと・ID採番）
        ↓
② 仕様から論理テストケースを作成・承認（実装非依存・ID紐付け）
        ↓
③ AIが中心的契約候補と対応テストケースを整理
        ↓
④ 人間が中心的契約をレビュー・承認
        ↓
⑤ 承認済み契約から最小TDD計画を作成・承認
        ↓
⑥ 実テストコードでRedを確認し、最小実装でGreenにする
        ↓
⑦ リファクタ
```

適用は2ケースに分かれる。

- **ケースA: 新規機能**（実装がまだ存在しない）→ ①〜⑦をそのまま順守できる、本来のTDD
- **ケースB: 既存の未テスト実装にテストを追加する**（retrofit）→ ①の前に実装を読んでよいが、
  実装から独立した情報源で仮説を立ててから読む、という順序が重要（詳細は後述）

---

## ケースA: 新規機能

### ① 仕様をMarkdownで記録する

- 置き場所: `docs/specs/<feature-slug>.md`（プロジェクトの慣習に合わせて調整可）
- **機能ごとに1ファイル**。要求はレイヤーを横断するため、layer別ではなくfeature単位で書く
- 機能ごとに短い英大文字プレフィックスを割り当てる（例: `RESET` = パスワードリセット機能）
- 仕様項目のID: `<PREFIX>-<3桁連番>`（例: `RESET-001`）。**1項目 = 1つの独立して検証可能な
  振る舞い**。粒度が大きすぎるとテストケースに落とせず、小さすぎると実装の詳細になる
- 一度採番したIDは項目を削除しても欠番のまま永久欠番にする（連番を詰め直さない。過去の
  テストケースやコミットからの参照が壊れるため）

テンプレート:

```markdown
# <機能名> 仕様（<PREFIX>）

## 概要
（何のための機能か、1〜2文）

## 仕様項目

| ID | 内容 | 想定レイヤー/モジュール | 備考 |
|---|---|---|---|
| RESET-001 | 有効なメールアドレス宛にリセットトークンを発行する | サービス層 | トークン有効期限は要確認 |
| RESET-002 | 存在しないメールアドレスを指定してもエラーを返さない（列挙攻撃対策） | サービス層 | |
| RESET-003 | 有効期限切れのトークンでリセットを試みると拒否される | サービス層 | |

## 確認事項
（曖昧・未決定の項目。ここが空になるまで②に進まない）
```

「想定レイヤー/モジュール」は実装前の仮説でよい（後で変わってもよい）。

### ② 仕様から論理テストケースを作成する

- 置き場所: 仕様ファイルと同じディレクトリに `<feature-slug>-test-cases.md`
- ID: `<spec-id>-TC<連番>`（例: `RESET-001-TC1`）。1つの仕様項目に対し、正常系・境界値・
  異常系など複数のTCがぶら下がってよい
- **関数名・エンドポイント名・コンポーネント名など実装の詳細は書かない。** 「前提」「操作」
  「期待結果」はすべてドメインの言葉で書く。これが成立するかどうかが、独立した仕様検証に
  なっているかのリトマス試験紙になる（「実装を見ないと書けないアサーションになっていないか」
  を自問する）

テンプレート:

```markdown
# <機能名> 論理テストケース（<PREFIX>）

| Test Case ID | 対応仕様ID | 前提 | 操作 | 期待結果 |
|---|---|---|---|---|
| RESET-001-TC1 | RESET-001 | 登録済みメールアドレスが存在する | パスワードリセットを要求する | リセットトークンが発行され、メールが送信される |
| RESET-002-TC1 | RESET-002 | 未登録のメールアドレスである | パスワードリセットを要求する | エラーを返さず、登録済みの場合と同じレスポンスになる |
| RESET-003-TC1 | RESET-003 | 有効期限切れのトークンが存在する | そのトークンでリセットを試みる | 拒否され、パスワードは変更されない |
```

作成後、以下をチェックする（トレーサビリティ確認）:
- 全ての仕様項目が最低1つのTCを持っているか
- 全てのTCが対応する仕様IDを持っているか

### ③ 確認粒度のルール

- **機械的に導出できるTC**（パラメータ違いの正常系、明らかな境界値など）はまとめて提示してよい
- **仕様書の「確認事項」に残っている項目**、**判断が分かれうる境界値・排他条件**は、
  1件ずつユーザーに質問して一緒に決める。「推奨案でまとめて進めますか？」で済ませない
- すべての確認事項を解消し、人間が論理テストケースを承認してから④に進む（Logical Test Case Gate）

### ④ 中心的契約候補を整理する

論理テストケースが人間に承認された後、AIは [中心的契約選定フロー](./CORE-CONTRACT-SELECTION.md) に従って全ケースをスクリーニングする。

- 同じ外部契約を検証するテストケースをまとめる
- 機能目的、主要正常系、重大リスク、新設・変更契約、実装方式によらない観測可能な振る舞いを候補にする
- 候補ごとに仕様ID、論理テストケースID、選定理由、既存保護、TDD適格性を記録する
- 候補外のケースには、実装後テストなどの検証先と理由を記録する
- 判断できない項目は仕様不足として提示し、推測で確定しない

人間が候補を修正・追加・除外し、中心的契約と対応テストケースを承認した時点でCore Contract Gateを通過する。承認前は最小TDD計画、テストコード、実装コードの作成へ進まない。

### ⑤〜⑦ TDDサイクルへ

1. 仕様書の確認事項が解消され、人間が仕様を承認済みであることを確認する（Specification Gate）
2. 人間が論理テストケースと仕様との対応を承認する（Logical Test Case Gate）
3. AIが中心的契約候補と対応テストケースを整理し、人間が承認する（Core Contract Gate）
4. AIが承認済み中心的契約から最小テストセットを選び、人間がテスト計画を承認する（Test Plan Gate）
5. AIが選定済みTCをテストコードへ翻訳する。テスト名にTC IDを含め、中心的契約と仕様項目へ遡れるようにする
6. 対象テストを実行し、意図した理由による失敗であることを確認して記録する（Red Gate）
7. 環境・fixture・モックなどが原因なら実装へ進まず、テスト基盤を修正してValid Redを取り直す
8. AIが仕様を満たす最小実装を書いて対象テストをgreenにする
9. テストを緩和せずリファクタし、対象テストのgreenを維持する
10. TDD Greenを記録し、最小垂直スライス開発フローの実装後テスト分析へ進む（TDD Green Gate）

## ケースB: 既存の未テスト実装にテストを追加する（retrofit）

実装が先に存在するため、純粋なTDDの順序（テストが先）は物理的に不可能。代わりに以下を守る。

1. テスト・Lint・型チェックの既存結果をBaselineとして記録し、既存失敗を分離する
2. **実装コードを開く前に**、README・プロジェクトのCLAUDE.md・API契約（OpenAPIスキーマ等）
   など、実装から独立した情報源だけで期待動作の仮説を書く（①のテンプレートを使う）
3. 実装コードを読み、2の仮説と突き合わせる。一致しない箇所・仮説が書けなかった箇所（＝
   実装を見ないと判断できなかった箇所）を「確認事項」として明示的にリストアップする
4. 確認事項は③のルールに従い、1件ずつユーザーに確認して確定させる
5. 確定した仕様から②の論理テストケースを作成し、人間の承認を得る
6. AIが中心的契約候補と対応テストケースを整理し、人間が承認する（Core Contract Gate）
7. AIが承認済み中心的契約から最小テストセットを選ぶ
8. 人間がテスト計画を承認した後、AIがテストを実装し、Valid RedまたはRed例外を確認・記録する
9. **テストが落ちたら、必ず以下のどちらかに分類して報告する**（無言でアサーション側を
   実装に合わせて緑にしない）:
   - **① 実装のバグ**: 仕様変更が不要であることを確認したうえで、実装を修正する
   - **② 仕様の理解違い**: 3に戻ってユーザーと再確認する
10. AIが実装・リファクタを行ってTDD Greenを記録し、最小垂直スライス開発フローの実装後テスト分析へ進む

## このテンプレートの使い方（他プロジェクトへの導入）

1. このファイルを新しいリポジトリの `docs/TDD-WORKFLOW.md`（など任意の場所）にコピーする
2. そのプロジェクトのCLAUDE.mdに、このファイルへの参照と、プロジェクト固有の情報
   （ディレクトリ構成・層構造・担当分担があればそれも）を書く
3. 仕様ファイル・論理テストケース・中心的契約選定・最小TDDテスト計画の置き場所（`docs/specs/`等）は、プロジェクトの
   慣習に合わせて調整してよい。ID採番ルール（`<PREFIX>-<連番>` / `<spec-id>-TC<連番>`）は
   そのまま踏襲することを推奨する（プロジェクトを跨いで同じ読み方ができるため）

# TDDワークフロー（仕様確定 → 論理テストケース → TDD計画 → 実装）

## 目的

この文書は、期待される振る舞いを実装コードから独立して言語化し、論理テストケースを唯一の真実として、実装前の最小TDDを進める手順を定める。

実装を先に書き、その実装に合わせて仕様やテストを後付けしない。TDDの事前テストは網羅的なテストスイートではなく、承認済みの中心的契約を実行可能なガードレールへ変換する。

## この文書のスコープ

この文書は、垂直スライス開発サイクルのうち、仕様と論理テストケースの確定から、中心的契約の選定、最小TDD計画、Red-Green-Refactorまでを扱う。

TDD Greenは機能全体のテスト完了を意味しない。以後は [最小垂直スライス開発フロー](./VERTICAL-SLICE-DEVELOPMENT-WORKFLOW.md) に戻り、実装後の単体・コンポーネント・統合・E2Eテストと全体検証を行う。

テストの選定・品質・最小性には、[最小TDDにおけるテスト作成原則](./MINIMUM-TDD-TEST-PRINCIPLES.md)を適用する。中心的契約の抽出と承認には、[中心的契約選定フロー](./CORE-CONTRACT-SELECTION.md)を適用する。

## 3ファイル構成

機能ごとのテスト設計と記録は、次の3ファイルで管理する。

| ファイル | 作成時期 | 責務 |
|---|---|---|
| `docs/specs/<feature-slug>-test-cases.md` | 仕様承認後 | 実装非依存の論理テストケース全体。期待動作の唯一の真実 |
| `docs/specs/<feature-slug>-tdd-plan.md` | 論理テストケース承認後 | 中心的契約選定、Baseline、最小TDD計画、Red/Green記録 |
| `docs/specs/<feature-slug>-post-test-report.md` | TDD Green・実装完了後 | 非TDDケースの引き継ぎ、実装分析、追加テスト、全体検証 |

機能仕様 `docs/specs/<feature-slug>.md` は、これらのテスト文書より上位のsource of truthである。

### 論理テストケースを唯一の真実にする

論理テストケースファイルは「何を保証するか」だけを扱う。

- Test Case ID
- 対応仕様ID
- 前提
- 操作
- 期待結果

TDD計画と実装後テストレポートは派生文書であり、期待結果を独自に定義または変更しない。論理テストケースの文章を複製せず、Test Case IDで参照し、次の実行情報だけを追加する。

- 選定理由または候補外理由
- テストレベル
- 実テストの場所
- Red例外
- 実行結果
- 対象外理由

期待結果の変更が必要な場合は、仕様と論理テストケースへ戻り、人間の再承認を得る。

### 参照版を固定する

TDD計画と実装後テストレポートには、参照した論理テストケースのファイルパスとコミットSHAを記録する。

参照後に論理テストケースが変更された場合、影響するCore Contract Gate、Test Plan Gate、実装後テスト分析の判定を無効として再確認する。

## 運用ゲート

1. **Specification Gate**: Blockingな仕様不足がなく、人間が仕様Markdownを承認している
2. **Logical Test Case Gate**: 仕様とのトレーサビリティを持つ論理テストケース全体を人間が承認している
3. **Core Contract Gate**: AIが全論理テストケースをスクリーニングし、人間が中心的契約と対応Test Case IDを承認している
4. **Test Plan Gate**: Baselineを確認し、AIが承認済み中心的契約から作成した最小TDDテストセットを人間が承認している
5. **Red Gate**: 実装変更前に、対象テストが意図した理由で失敗することを確認・記録している
6. **TDD Green Gate**: 承認済みの最小TDDテストを緩和せず通し、リファクタ後もGreenを維持している

Characterization Test、既存テストによる保護、純粋なリファクタリングではRed Gateを省略できるが、原則書に定める例外理由をTDD計画へ記録する。

## 全体像

```
① 仕様をMarkdownで記録・承認
        ↓
② 論理テストケース全体を作成・承認
        ↓
③ TDD計画をDraftで作成
        ↓
④ AIが中心的契約候補と対応Test Case IDを整理
        ↓
⑤ 人間が中心的契約をレビュー・承認
        ↓
⑥ Baselineを確認し、最小TDDテストセットを承認
        ↓
⑦ Red → Green → Refactor
        ↓
⑧ 実装後テスト分析へ引き継ぐ
```

## ケースA: 新規機能

### 1. 仕様をMarkdownで記録する

- 置き場所: `docs/specs/<feature-slug>.md`
- 機能ごとに1ファイルとし、レイヤー別ではなく垂直スライス単位で書く
- 各仕様項目に `<PREFIX>-<3桁連番>` のIDを付ける
- Blockingな確認事項を解消し、人間が承認する

### 2. 論理テストケース全体を作成する

- 置き場所: `docs/specs/<feature-slug>-test-cases.md`
- IDは `<spec-id>-TC<連番>` とする
- 関数名、エンドポイント名、コンポーネント名などの実装詳細を書かない
- すべての仕様IDに1件以上のTest Case IDを対応させる
- すべてのTest Case IDを仕様IDへ追跡可能にする
- 人間が仕様との一致と過不足を承認する

機械的に導出できるケースはまとめて提示してよい。判断が分かれる境界値、排他条件、失敗時の状態は、1件ずつ人間と決める。

### 3. TDD計画をDraftで作成する

[最小TDDテスト計画テンプレート](./templates/minimum-tdd-test-plan.md)をコピーし、`docs/specs/<feature-slug>-tdd-plan.md` として保存する。

この時点では中心的契約選定セクションから記入し、最小TDDテストセットを先に確定しない。

### 4. 中心的契約を選定する

AIは承認済みの全論理テストケースをスクリーニングし、中心的契約候補と対応Test Case IDをTDD計画へ記録する。

- 同じ外部契約を検証する論理テストケースをまとめる
- 選定条件、既存保護、TDD適格性を記録する
- 候補外ケースには理由と実装後の検証先を記録する
- 判断できない項目は仕様不足として提示する
- 人間が候補を修正・追加・除外し、中心的契約を承認する

Core Contract Gate通過前に、最小TDDテストセット、テストコード、実装コードを確定しない。

### 5. Baselineを確認する

Baselineは垂直スライスの主Phaseではなく、最初のテストコードまたは実装コード変更前に行う技術的チェックである。

対象に応じて、関連する既存テスト、Lint、型チェック、ビルドを実行し、TDD計画へ次を記録する。

- 基準としたコミットSHA
- 実行コマンドと結果
- 既存失敗
- 実行しなかった検証と理由

Baselineの目的は、既存失敗と今回のRed・回帰を区別し、既存テストによる保護が実際に機能していることを確認することである。仕様作成や論理テストケース作成だけのPRでは、コード変更用のBaselineを要求しない。

Baselineに失敗がある場合は、対象機能の変更と分離できるかを判断する。分離できない場合は、先に修正するか、既存問題として扱うかを人間と決める。

### 6. 最小TDDテストセットを承認する

AIは承認済み中心的契約から、変更目的、重大反例、代表回帰を識別する必要最小限のテストを選ぶ。

既存テストで中心的契約を十分に保証できる場合は、新規テストを形式的に追加せず、既存テストIDと根拠を記録する。

人間がテストレベル、Test Case ID、Contract ID、Red例外、既存保護をレビューし、Test Plan Gateを通過させる。

### 7. Red-Green-Refactorを行う

1. AIが選定済みTest Case IDをテストコードへ翻訳する
2. テスト名またはテストメタデータからTest Case IDへ遡れるようにする
3. 対象テストを実行し、意図した理由によるValid Redを記録する
4. 環境、fixture、mockの不備による失敗はRedとして扱わない
5. AIが仕様を満たす最小実装を書いてGreenにする
6. テストを緩和せずリファクタし、Greenを維持する
7. TDD Greenを記録し、実装後テスト分析へ進む

## ケースB: 既存の未テスト実装にテストを追加する

既存実装へのretrofitでは、純粋なTDDの順序を再現できない。次を守る。

1. 実装コードを正解とみなさず、README、仕様、API契約など独立した情報源から期待動作の仮説を作る
2. 実装を読み、仮説との不一致と未定義動作を確認事項として整理する
3. 人間と仕様を確定し、論理テストケース全体を作成・承認する
4. 新規機能と同じTDD計画を作成し、中心的契約を選定・承認する
5. 最初のテストコードまたは実装コード変更前にBaselineを記録する
6. 最小TDDテストセットを承認し、Valid Redまたは正当なRed例外を記録する
7. テスト失敗を、実装のバグまたは仕様理解の違いに分類する
8. 仕様理解の違いであれば、仕様と論理テストケースへ戻って再承認する
9. AIが実装・リファクタを行い、TDD Greenを記録する

Characterization Testは追加時点からGreenでよいが、現在の挙動という理由だけで正しい仕様として固定しない。

## 実装後テストへの引き継ぎ

TDD Green・実装完了後、[実装後テストレポートテンプレート](./templates/post-implementation-test-report.md)をコピーし、`docs/specs/<feature-slug>-post-test-report.md` として作成する。

次を入力として実装後テストを整理する。

- TDD計画で候補外または実装後へ送ったTest Case ID
- TDDで保証したTest Case ID
- 実装とカバレッジの分析で見つかった分岐、境界、エラー処理、接続リスク
- 実装中に判明した新しいリスク

新しい利用者向け振る舞いまたは仕様から期待結果を導けないケースが見つかった場合、実装後テストだけで期待結果を確定しない。仕様と論理テストケースへ戻り、人間の再承認を得る。

Slice Complete前に、すべての論理Test Case IDが、TDD、実装後テスト、既存テスト、または根拠付き対象外のいずれかへ割り当てられていることを確認する。

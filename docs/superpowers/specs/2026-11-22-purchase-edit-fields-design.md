## 1. 目的と背景

登録では`unit`（購入単位）と`buffer_days`（余裕日数）を入力できるが、編集ダイアログとPUTは受け付けない。入力を間違えても直せず、単位を変えたいときは登録し直すしかない。これはPTFスライスが「編集は未仕様化」として意図的に持ち越した課題である（PTF §7）。

また、編集（PUT）の検証は登録（POST）と食い違っている。

| 項目 | 登録（POST） | 編集（PUT）の現状 |
|---|---|---|
| `name` / `category` | 50 / 30文字まで、空白だけは拒否 | 上限なし、空白だけも通る |
| `days_per_unit` | 0以上365以下の整数 | 0より大きい実数（0は拒否、小数・上限超過を許す） |
| `stock` | 0以上100,000以下の整数 | 0以上の実数（小数・上限超過を許す） |
| `is_temporary` | 必須の真偽値 | 省略すると`false` |

そのため、登録では拒否される値を、編集経由なら保存できる。

## 2. ゴール・非ゴール・アンチゴール

### ゴール

- 編集ダイアログで、登録で入力できる全項目（`unit`・`buffer_days`を含む）を変更できる
- 同じ入力は、登録と編集で同じ判定（受理・拒否）になる

### 非ゴール

- 変更したい項目だけを送る部分更新（PATCH）
- 既存データの移行（現在は本番データがなく、開発用DynamoDB Localのデータは作り直す）
- 購入タイミング・購入数量の計算、在庫の入れ直し（①-2、①-3）

### アンチゴール

- 編集で`stock_counted_at`、`created_at`、`id`が意図せず変わること
- 既存の編集の振る舞い（重複の拒否、同時編集時の再試行、存在しないIDの404）が崩れること

## 3. 採用した方式

| 案 | 内容 | 判断 |
|---|---|---|
| A | PUTを全項目必須の完全置き換えにし、登録と同じ検証定義を共有する | **採用**（2026-11-22 ym28-it） |
| B | `unit`・`buffer_days`を任意にし、省略時は保存済みの値を引き継ぐ | 不採用。PUTに部分更新の例外が混ざり、検証の定義も二重になる |
| C | 変更項目だけ送るPATCHへ切り替える | 不採用。今回の範囲を超えるAPI設計の変更。別スライスとする |

案Aを選んだ理由: 目的が「登録と編集で同じルールにする」ことなので、定義を1か所にそろえるのが最も直接的である。PUTの呼び出し元はこのリポジトリのフロントエンドとE2Eだけで、破壊的変更の影響が小さい。

## 4. 仕様

### 4.1 編集で受け付ける項目

登録（PTF §4.1）と同じ項目・制約とする。

| 項目 | API名 | 必須 | 許容値 | 上限 |
|---|---|---|---|---|
| 名前 | `name` | 必須 | 空白文字だけではない文字列 | 50文字 |
| カテゴリ | `category` | 必須 | 空白文字だけではない文字列 | 30文字 |
| 購入単位 | `unit` | 必須 | 空白文字だけではない文字列 | 10文字 |
| 1単位あたりの日数 | `days_per_unit` | 必須 | 0以上の整数 | 365 |
| 余裕日数 | `buffer_days` | 必須 | 0以上の整数 | 30 |
| 在庫（購入単位） | `stock` | 必須 | 0以上の整数 | 100,000 |
| 一時的な購入 | `is_temporary` | 必須 | 真偽値 | - |

### 4.2 仕様項目

| ID | 内容 |
|---|---|
| PEDT-001 | 編集（PUT）は、4.1の全項目を必須とする完全置き換えとする。リクエストに`unit`・`buffer_days`を含め、`is_temporary`の省略時の既定値（`false`）は廃止する。`stock_counted_at`・`created_at`・`id`はクライアントから受け取らない |
| PEDT-002 | 同じ入力は、登録と編集で同じ判定（受理・拒否）になる。文字列の扱い（正規化しない、前後空白を除去しない、コードポイント単位で数える）、整数のみ・小数表記・文字列・負数・上限超過の拒否（丸めない）は、PURC第3版・PTF-005・PTF-014と同じとする |
| PEDT-003 | 編集で`days_per_unit`に0を指定できる（PTF-002と同じ。従来のPUTの「0より大きい」は廃止する） |
| PEDT-004 | 入力制約違反と必須項目の欠落は、登録と同じく422で、項目ごとに識別できる情報を返す |
| PEDT-005 | 編集成功時、`unit`・`buffer_days`を含む全項目を保存し、レスポンスは登録・一覧と同じ形（`stock_counted_at`、作成日時、更新日時を含む）とする。作成日時は変えない |
| PEDT-006 | `stock_counted_at`は、在庫が保存済みの値から変わったときだけ更新する（PTF-013を維持）。`unit`や`buffer_days`だけの変更では更新しない |
| PEDT-007 | 編集ダイアログに購入単位と余裕日数の入力欄を加え、全項目の初期値は保存済みの値とする。項目名と説明は、登録画面と同じく購入単位で数える値であることが読み取れるものにする（PTF-010） |
| PEDT-008 | 編集ダイアログの入力検証（必須、整数のみ、範囲、文字数、空白だけの拒否）は、登録ダイアログと同じ結果になる。違反時はサーバーへ送らず、項目ごとにエラーを表示する |
| PEDT-009 | 重複判定（名前とカテゴリの完全一致で409、`unit`は含めない）、存在しないIDの404、同時編集時の読み直しと再試行は変えない（PTF-016、PURC第3版） |
| PEDT-010 | PTF-012の「編集で`unit`と`buffer_days`を失わない」を、PEDT-001・PEDT-005で置き換える（削除操作が`days_per_unit`を扱う部分は変わらない） |

### 4.3 API契約

- 編集（PUT）のリクエスト: `name`、`category`、`unit`、`days_per_unit`、`buffer_days`、`stock`、`is_temporary`（すべて必須）
- 編集のレスポンス: 登録・一覧と同じ（ID、入力項目、`stock_counted_at`、作成日時、更新日時。利用者IDは含めない）
- 成功は200。422・404・409は上記のとおり
- 検証の定義は、登録と編集で共有する（実装方法は任せる）

## 5. 成果物とテストへの影響

- `docs/specs/purchase-create.md`は変更しない。編集の仕様はこの設計書（PEDT）に置く
- 論理テストケース（`2026-11-22-purchase-edit-fields-test-cases.md`）とTDD計画を`design-tdd-tests`で作成する
- 既存の編集テスト（PUTで`unit`・`buffer_days`を送らない前提のもの、`days_per_unit`の0拒否や小数許容を前提にしたもの）は、この設計の承認を根拠に書き直す
- `frontend/src/api/schema.d.ts`をバックエンドのOpenAPIから再生成する。E2Eは編集の操作に合わせて更新する

## 6. 確認事項

### Blocking

- なし

### Important

- **`unit`だけを変えて在庫の数値を変えない編集**: 数える単位が変わるので在庫の意味も変わるが、特別な警告や補正はしない。`stock_counted_at`も更新しない（PEDT-006）。（設計者の判断）

### Deferred

- 変更項目だけ送る部分更新（PATCH）
- 編集履歴・取り消し
- 在庫の入れ直しの記録（①-3）

## 8. 設計者の判断（確認してください）

- 既存データの移行を行わない（本番データなし、開発用DBは作り直す）
- `unit`だけの変更では`stock_counted_at`を更新しない
- `days_per_unit = 0`を編集でも許可する（従来のPUTより緩くなる）
- 重複判定に`unit`を含めない（現状維持）

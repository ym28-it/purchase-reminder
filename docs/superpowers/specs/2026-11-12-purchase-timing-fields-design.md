# 購入タイミング計算用の登録項目（PTF）設計

## メタデータ

| 項目 | 値 |
|---|---|
| 状態 | Draft（Blocking 0件、承認待ち） |
| 仕様プレフィックス | `PTF` |
| 対象スライス | ①-1 登録項目の変更（登録画面 → 登録API → DB） |
| 改訂対象 | 購入物登録・一覧反映仕様（PURC）第2版 → 第3版 |
| 作成日 | 2026-11-12 |

## 1. 目的と背景

買い物リマインダーは、次に買い物へ寄れる時までに切れるものを判定し、何をいくつ買うかを伝える。
その計算（①-2 買い物計画の表示）に必要な値を、購入物の登録時にそろえるのがこのスライスの目的である。

利用者（1人）は平日ならいつでも、仕事帰りの18:30以降に買い物へ寄れる。
消費の速さは「1購入単位を何日で使い切るか」（例: 牛乳は1パック3日）で捉えている。
現在の`speed`は単位が定義されておらず、`speed`（速さ）という名前と「1単位あたりの日数」という意味が逆向きになる。

## 2. ゴール・非ゴール・アンチゴール

### ゴール

- 登録時に、購入単位の名前、1単位あたりの日数、余裕日数、在庫（購入単位）を入力できる
- 在庫を数えた日時をサーバーが記録し、後続スライスの計算の起点にできる
- API・DB・画面の項目名が意味と一致する

### 非ゴール

- 購入タイミング・購入数量の計算と買い物計画画面（①-2）
- 在庫の入れ直しとその記録（①-3）
- 消費スピード・余裕日数を編集する画面と操作（編集スライス、未仕様化）
- 既存データの移行（開発環境のDynamoDB Localのデータは作り直す）

### アンチゴール

- 項目名を変えたことで、PURC第2版で守っていた登録の振る舞い（重複拒否、エラー表示、画面の動き）が崩れること
- 既存の編集・削除操作が、新しい項目を消したり壊したりすること

## 3. 採用した方式

| 案 | 内容 | 判断 |
|---|---|---|
| A | `speed`の名前を残し、意味と範囲だけ変える | 不採用。名前と意味が逆向きのまま①-2以降へ残る |
| B | `speed`を`days_per_unit`へ改名し、`buffer_days`と`stock_counted_at`を追加する | **採用**（2026-11-12 ym28-it） |
| C | 登録は変えず、別の設定画面で新項目を入れる | 不採用。計算に必要な値が1件の登録でそろわず、経路が1本増える |

案Bを選んだ理由: 利用者が1人で、移行すべき本番データがない今が改名の費用が最も小さい。Pydanticスキーマを API 契約の source of truth とする方針とも合う。

## 4. 仕様

### 4.1 入力項目（PURC第2版からの変更点）

| 項目 | API名 | 必須 | 許容値 | 上限 | 初期値 |
|---|---|---|---|---|---|
| 名前 | `name` | 必須 | 変更なし | 50文字 | 空 |
| カテゴリ | `category` | 必須 | 変更なし | 30文字 | 空 |
| 購入単位 | `unit` | 必須 | 空白文字だけではない文字列 | 10文字 | 空 |
| 1単位あたりの日数 | `days_per_unit` | 必須 | 0以上の整数 | 365 | 0 |
| 余裕日数 | `buffer_days` | 必須 | 0以上の整数 | 30 | 0 |
| 在庫（購入単位） | `stock` | 必須 | 0以上の整数 | 100,000 | 0 |
| 一時的な購入 | `is_temporary` | 必須 | 変更なし | - | false |

### 4.2 仕様項目

| ID | 内容 |
|---|---|
| PTF-001 | 消費スピードは「1購入単位を何日で使い切るか（日）」を表し、API・DB・画面では`days_per_unit`として扱う。旧名`speed`はAPIで受け付けず、レスポンスにも含めない |
| PTF-002 | `days_per_unit`は0以上365以下の整数とする。0は購入時期の計算対象外を表す（PURC第2版の「消費スピード0」の意味を引き継ぐ） |
| PTF-003 | 余裕日数`buffer_days`は0以上30以下の整数で、登録時に必須とする。画面の初期値は0とする |
| PTF-004 | 在庫`stock`は購入単位で数えた量とする。許容値と上限はPURC第2版から変えない |
| PTF-005 | `days_per_unit`と`buffer_days`は、`stock`と同じくJSONの整数値だけを受け付け、小数表記・文字列・負数・上限超過を丸めずに拒否する（PURC-004と同じ扱い） |
| PTF-006 | 登録時、サーバーは在庫を数えた日時`stock_counted_at`を記録する。値は作成日時と同じ時刻とし、クライアントからは受け取らない |
| PTF-007 | `stock_counted_at`は`updated_at`とは別に保持する。名前やカテゴリの変更では更新しない |
| PTF-008 | 登録成功時のレスポンスには`unit`、`days_per_unit`、`buffer_days`、`stock_counted_at`を含める |
| PTF-009 | 一覧には名前、カテゴリ、購入単位、1単位あたりの日数、余裕日数、在庫、一時的な購入かどうかを表示する（PURC-012を置き換える）。`stock_counted_at`は一覧に表示しない |
| PTF-010 | 登録画面の項目名と説明は、1単位あたりの日数・余裕日数・在庫が購入単位であることを利用者が読み取れるものにする。具体的な文言は固定しない |
| PTF-011 | 一覧取得（GET）のレスポンスにも`unit`、`days_per_unit`、`buffer_days`、`stock_counted_at`を含める |
| PTF-012 | 既存の編集（PUT）・削除操作は、改名に合わせて`days_per_unit`を扱う。編集で`unit`と`buffer_days`を失わない |
| PTF-013 | 編集（PUT）で在庫を保存済みの値から変えた場合、`stock_counted_at`を編集を保存した時刻に更新する。在庫が変わらない編集では更新しない。この更新は在庫の入れ直しの記録（①-3）には残さない |
| PTF-014 | 購入単位`unit`（例: パック、本）を登録時に必須で受け付ける。空白文字だけの値は拒否し、上限は10文字とする。文字列の扱い（正規化しない、前後空白を除去しない、コードポイント単位で数える）はPURC第2版の名前・カテゴリと同じとする |
| PTF-015 | `unit`は登録・一覧のレスポンスに含め、一覧では在庫と1単位あたりの日数を単位名付きで表示する（例: 在庫 2パック、1パック3日） |
| PTF-016 | `unit`は重複判定に含めない。名前とカテゴリが完全一致すれば、単位が違っても重複として拒否する（PURC-014をそのまま適用） |

PURC第2版のPURC-001〜024は、上の置き換え（PURC-002の入力項目数、PURC-004の対象項目、PURC-012の表示項目）を除いて第3版でもそのまま有効とする。

### 4.3 API契約

- 登録（POST）のリクエスト: `name`、`category`、`unit`、`days_per_unit`、`buffer_days`、`stock`、`is_temporary`
- 登録・一覧のレスポンス: ID、上記の入力項目、`stock_counted_at`、作成日時、更新日時（利用者IDは含めない）
- 入力制約違反は422で、項目ごとに識別できる情報を返す（PURC第2版と同じ）
- 409・その他の失敗の扱いはPURC第2版と同じ

## 5. 成果物とテストへの影響

- 仕様承認後、`docs/specs/purchase-create.md`を第3版に改訂し、PTFの変更を反映する。論理テストケース（`docs/specs/purchase-create-test-cases.md`）も第3版に合わせる

## 6. 確認事項

### Blocking

- なし

### 解決済み（2026-11-22 ym28-it）

- **BLK-1 編集（PUT）で在庫を変えたとき、`stock_counted_at`を更新するか** → 更新する（PTF-013）。記録は①-3の経路だけで残す
- **BLK-2 購入単位の名前を持つか** → 持つ（PTF-014〜016）

### Important

- なし

### Deferred

- 消費スピードと余裕日数の編集画面（編集スライス）
- 祝日や寄れない日の扱い（①-2）
- 朝の在庫確認の時刻と土日の扱い（③）

## 7. 実装者に任せる事項

- DynamoDBアイテムの属性名、日時の保存形式（既存の`created_at`と同じ形式に合わせる）
- 登録画面の項目の並びと説明文の文言（PTF-010の範囲内）
- 既存テストの書き直しの単位（ファイル分割など）
- 編集（PUT）の入力検証: 編集は仕様化されていないため、改名だけを行い既存の検証をそのまま残す。`unit`と`buffer_days`はPUTのリクエストに含めず、保存済みの値を引き継ぐ。単位を変えたい場合は登録し直す（設計者の判断）
- `unit`の上限10文字と、重複判定に含めないこと（PTF-014、PTF-016）（設計者の判断）

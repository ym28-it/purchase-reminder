## 1. 目的

利用者が購入時期を管理したい物品を登録し、登録結果を一覧から
確認できるようにする。

登録情報は、後続の購入時期計算、通知、在庫修正などの基礎データになる。

## 2. 垂直スライス

### 開始点

利用者が購入物一覧画面から追加操作を開始する。

### 終了点

登録した購入物が現在の利用者に紐づいて永続化され、
登録内容が購入物一覧に表示される。

## 3. 入力仕様

| 項目 | 必須 | 許容値 | 上限 | 初期値 |
|---|---|---|---|---|
| 名前 | 必須 | 空白文字だけではない文字列 | 50文字 | 空 |
| カテゴリ | 必須 | 空白文字だけではない自由入力 | 30文字 | 空 |
| 消費スピード | 必須 | 0以上の整数 | 100,000 | 0 |
| 現在の在庫 | 必須 | 0以上の整数 | 100,000 | 0 |
| 一時的な購入 | 必須 | true / false | - | false |

### 消費スピード0の意味

`speed = 0`は、その購入物を購入時期の計算対象外とすることを表す。

これは`is_temporary`とは独立した指定であり、定期購入する物品でも
消費スピード0を指定できる。

### 文字列の扱い

- 名前またはカテゴリが空白文字だけの場合は登録できない
- 入力文字列は正規化しない
- 前後空白を自動的に除去しない
- 大文字・小文字、全角・半角を同一視しない
- 文字数はUnicodeコードポイント単位で数える。例えば`𠮷`は1文字として数える

### 数値と真偽値の扱い

- 消費スピードと現在の在庫は、JSONの整数値だけを受け付ける。`1.0`のような小数表記や`"1"`のような文字列は、値が整数に等しくても拒否する
- 一時的な購入は、JSONの真偽値（`true` / `false`）だけを受け付ける。`"true"`や`1`は拒否する

## 4. 重複登録

同一利用者について、名前とカテゴリの両方が入力文字列として
完全一致する購入物を複数登録してはならない。

以下は別の購入物として扱う。

- `牛乳`と` 牛乳 `
- `Milk`と`milk`
- `Ｍｉｌｋ`と`Milk`

重複判定では、消費スピード、在庫、`is_temporary`の違いを考慮しない。

重複はフロントエンドの事前確認だけに依存せず、
同時登録が発生した場合もバックエンドの永続化処理で防止する。

## 5. 仕様項目

| ID | 内容 |
|---|---|
| PURC-001 | 利用者は購入物一覧から登録画面を開ける |
| PURC-002 | 登録画面で、仕様に定めた5項目を入力できる |
| PURC-003 | フロントエンドとAPIの両方が入力制約を検証する |
| PURC-004 | 小数、負数、上限超過値は丸めたり切り詰めたりせず拒否する |
| PURC-005 | 有効な入力に対して、現在の利用者に紐づく購入物を1件作成する |
| PURC-006 | ID、作成日時、更新日時はシステムが生成する |
| PURC-007 | 利用者IDはクライアントから受け取らず、サーバー側で決定する |
| PURC-008 | 登録成功時、APIはHTTP 201と作成された購入物を返す |
| PURC-009 | 登録された購入物は永続化され、再取得できる |
| PURC-010 | 登録成功後、登録画面を閉じて入力値を初期化する |
| PURC-011 | 登録成功後、一覧を最新の永続状態へ更新する |
| PURC-012 | 一覧には名前、カテゴリ、消費スピード、在庫、一時的な購入かどうかを表示する |
| PURC-013 | 登録処理中は登録操作を無効化し、同じ画面操作による重複送信を防ぐ |
| PURC-014 | 同一利用者の名前・カテゴリが完全一致する重複登録を拒否する |
| PURC-015 | 登録失敗時は登録画面を閉じず、すべての入力内容を維持する |
| PURC-016 | 判明している失敗原因は利用者が識別できる形で表示する |
| PURC-017 | 通信・サーバー障害では内部情報を表示せず、共通の失敗状態を表示する |
| PURC-018 | 通信失敗時に登録要求を自動再送しない |
| PURC-019 | ある利用者の購入物を別の利用者の一覧に含めない |
| PURC-020 | 登録画面を閉じて再度開いたとき、前回の登録失敗の表示を残さず、入力値を初期値で表示する |
| PURC-021 | 画面の入力検証を通過した後にAPIが入力制約違反を返した場合も、問題のある入力項目を項目ごとに識別できる形で表示する |
| PURC-022 | 購入物を削除した後、同じ利用者は同じ名前・カテゴリの購入物を再登録できる |
| PURC-023 | 編集で名前またはカテゴリを変更した場合、変更前の組で再登録できる。変更後の組が同じ利用者の別の購入物と完全一致する場合は409で拒否し、変更を永続化しない |
| PURC-024 | 同じ利用者の登録・編集・削除が同時に行われても、一覧に存在しない名前・カテゴリの組が登録できなくなることはない |

## 6. API契約

### 登録成功

- HTTPステータス：`201 Created`
- 作成した購入物をレスポンスとして返す

レスポンスには以下を含める。

- ID
- 名前
- カテゴリ
- 消費スピード
- 現在の在庫
- 一時的な購入かどうか
- 作成日時
- 更新日時

利用者IDはレスポンスへ含めない。

### 入力制約違反

- HTTPステータス：`422 Unprocessable Entity`
- 永続化を行わない
- 問題のある入力項目を識別できる情報を返す

### 重複登録

- HTTPステータス：`409 Conflict`
- 新しい購入物を永続化しない
- 重複登録であることを識別できる情報を返す
- 画面はHTTPステータスで重複を判定し、エラーメッセージの文言に依存しない

### 編集時の重複（PURC-023）

- 変更後の名前・カテゴリが同じ利用者の別の購入物と完全一致する場合、HTTPステータス：`409 Conflict`
- 編集内容を永続化しない

### その他の失敗

内部実装や機密情報を利用者向けエラーへ含めない。

## 7. 画面の振る舞い

### 登録成功

1. 登録処理中は登録ボタンを無効化する
2. APIの成功後に登録画面を閉じる
3. 入力値を初期化する
4. バックエンドから一覧を再取得する
5. 登録した購入物を一覧へ表示する
6. 追加の成功メッセージやトーストは表示しない

### 登録失敗

1. 登録画面を開いたままにする
2. すべての入力内容を維持する
3. 判明している原因を個別に表示する
4. その他の障害では共通エラーを表示する
5. 登録要求を自動再送しない
6. 利用者は同じ入力内容から手動で再試行できる

具体的な日本語文言は固定せず、原因と必要な対処が利用者に伝わることを契約とする。

## 8. 対象外

- 購入物の編集・削除の画面と操作（PURC-022〜024で定める一意性の維持を除く。編集画面での409の表示方法も対象外）
- 在庫の消費・補充
- 購入予定日や購入数量の計算
- 通知
- 一覧の並び順
- 検索、絞り込み、ページネーション
- カテゴリ候補の管理
- Cognito認証の実装
- 冪等性キーによる自動再送
- 本番AWS環境へのデプロイ
- UIの細かな色、余白、アニメーション

## 9. 受け入れ条件

- [ ] 有効な入力で購入物を1件登録できる
- [ ] 登録結果が現在の利用者に紐づいて永続化される
- [ ] 再取得後も登録結果が存在する
- [ ] 登録内容が一覧に表示される
- [ ] 空白だけの名前・カテゴリを登録できない
- [ ] 負数、小数、上限超過値を登録できない
- [ ] 消費スピード0を登録できる
- [ ] 完全一致する名前・カテゴリの重複を登録できない
- [ ] 登録処理中の重複送信が防止される
- [ ] 登録失敗時に入力内容が維持される
- [ ] 失敗原因が判明している場合は個別表示される
- [ ] 通信失敗時に自動再送されない
- [ ] 他の利用者の購入物が一覧に混在しない
- [ ] 登録画面を開き直すと前回の失敗表示が残らない
- [ ] APIの入力制約違反が項目ごとに表示される
- [ ] 削除後、または名前・カテゴリの編集後に、変更前の組で再登録できる
- [ ] 編集で別の購入物と同じ名前・カテゴリにすると409で拒否される
- [ ] 同時の登録・編集・削除の後も、一覧にない名前・カテゴリの組を登録できる

## 10. 残存リスク

通信切断前にサーバーで保存が完了し、成功レスポンスだけを受信できなかった場合、
利用者には失敗として見える可能性がある。

この場合の冪等性キーや自動的な結果照合は本スライスでは実装せず、
後続課題として扱う。

# 中心的契約選定フロー

## 1. 目的

この文書は、承認済みの仕様と論理テストケースから、実装前の最小TDDで保証する中心的契約を選定する手順を定める。

論理テストケース全体をそのまま事前TDDへ持ち込まず、AIが一定の条件で候補をスクリーニングし、人間がプロダクト上の重要性をレビューして最終決定する。これにより、最小TDDを実装の道筋とガードレールとして保ちながら、中心的契約の決定責任を人間に残す。

## 2. このレイヤーの位置づけ

中心的契約選定は、論理テストケースの承認後、最小TDDテスト計画の作成前に行う。

1. 仕様を作成・承認する
2. 論理テストケースを作成・承認する
3. AIが中心的契約候補と対応テストケースを整理する
4. 人間が候補をレビューし、修正・承認する
5. 承認済み中心的契約から最小TDDテスト計画を作成する
6. テストコード、実装、実装後テストへ進む

選定中に仕様の曖昧さや矛盾が見つかった場合は、中心的契約を推測で確定せず、仕様または論理テストケースへ戻って修正し、人間の再承認を得る。

## 3. 中心的契約の定義

中心的契約とは、実装方式が変わっても維持されるべき、利用者または外部境界から観測可能な振る舞いのうち、その変更の目的または重大なリスクを代表する契約である。

中心的契約と論理テストケースは同一ではない。1つの中心的契約を正常系、重大反例、統合経路など複数の論理テストケースが検証する場合がある。

## 4. 選定条件

AIはすべての論理テストケースを確認し、対応する契約が次の条件の1つ以上に該当する場合、中心的契約候補として提示する。

1. 失敗すると、その機能の利用目的を達成できない
2. 必要な既存・新規レイヤーを通る主要な正常系を規定している
3. データ不整合、権限逸脱、重複など、発生時の影響が大きい、または修復が難しい状態を防ぐ
4. 今回新設または変更され、既存テストでは十分に保証されていない
5. 実装方式が変わっても維持すべき、利用者または外部境界から観測可能な振る舞いである

候補は、確定した仕様に根拠を持ち、実装詳細を不必要に固定してはならない。条件への該当は自動承認を意味せず、人間のレビューによって中心的契約として確定する。

## 5. TDD対象としての適格性

中心的契約候補に対応する論理テストケースを最小TDD候補にするには、次を満たす必要がある。

- 実装前の期待結果を承認済み仕様から一意に導ける
- 未実装または誤実装による失敗理由を事前に説明できる
- 環境構築、fixture、mockの不備ではなく、契約の不成立によってRedになる
- 自動テストとして決定的かつ独立して検証できる
- 適切なテストレベルで、破られた契約を特定できる
- 最小実装へ段階的に進められる粒度である

既存挙動を保護するCharacterization Test、既存テストによる保護、純粋なリファクタリングはRedの例外になり得る。例外は最小TDDテスト計画へ理由を記録する。

## 6. AIによるスクリーニング手順

AIは次の順序で候補を整理する。

1. 承認済み仕様IDと論理テストケースIDを一覧化する
2. 同じ外部契約を検証する論理テストケースをまとめる
3. 各契約を選定条件とTDD適格性に照らして評価する
4. 中心的契約候補、候補外、判断保留に分類する
5. 候補ごとに対応仕様ID、対応テストケースID、選定理由、既存保護を記録する
6. 候補外にしたものは、実装後テストなど後続の検証先と理由を記録する
7. 判断保留は仕様不足として分類し、必要な確認事項を提示する
8. 人間へ選定案を提示する

AIはテスト本数を先に決めて候補を切り捨てない。契約を先に選び、その契約を識別できる必要最小限のテスト数を後続の最小TDD計画で決める。

## 7. 人間によるレビューと承認

中心的契約の最終決定責任は人間が持つ。人間は次をレビューする。

- 機能の目的を代表する契約が含まれている
- プロダクト上許容できない重大リスクが含まれている
- 優先度の低い詳細や網羅目的のケースが中心へ入り込んでいない
- 候補外とした契約の後続検証先が妥当である
- 対応する仕様IDと論理テストケースIDが正しい
- 仕様上の判断をAIが暗黙に追加していない

人間は候補の承認、修正、追加、除外を行える。承認されるまでは、AIは最小TDDテスト計画、テストコード、実装コードの作成へ進まない。

## 8. 成果物

[中心的契約選定テンプレート](./templates/core-contract-selection.md)をコピーし、仕様ファイルと同じ `docs/specs/` に `<feature-slug>-core-contracts.md` として保存する。

各中心的契約には `<PREFIX>-CORE-<3桁連番>` のIDを付ける。IDは承認後に変更・再利用せず、削除した場合も欠番とする。

成果物には少なくとも次を記録する。

- 対応する仕様と論理テストケース文書
- 中心的契約候補と選定条件
- 対応仕様IDと論理テストケースID
- 既存テストによる保護状況
- TDD適格性とRed例外
- 候補外の契約と後続の検証先
- 未解決の判断
- 人間による承認者、承認日、承認状態

## 9. Core Contract Gate

次をすべて満たしたとき、Core Contract Gateを通過する。

- [ ] 仕様と論理テストケースが人間に承認されている
- [ ] すべての論理テストケースをスクリーニングしている
- [ ] 各中心的契約に仕様IDと論理テストケースIDが対応している
- [ ] 各候補の選定理由が選定条件に対応している
- [ ] 候補外の重要なケースに後続の検証先と除外理由がある
- [ ] Blockingな仕様不足または判断保留が残っていない
- [ ] 人間が中心的契約と対応テストケースを承認している

承認後、AIはすべての中心的契約を少なくとも1つのテストで識別できるよう、最小TDDテスト計画を作成する。ただし既存テストで十分に保証される契約は、根拠を記録したうえで新規テストを省略できる。

## 10. 責務

### 人間

- 機能目的とプロダクト上の優先順位を判断する
- 中心的契約候補を修正・追加・除外する
- 中心的契約と対応テストケースを最終承認する

### AI

- 仕様と全論理テストケースを選定条件に従ってスクリーニングする
- 候補、根拠、対応ID、既存保護、候補外の検証先を整理する
- 仕様不足を推測で埋めず、人間へ確認する
- 承認済み中心的契約から最小TDDテスト計画を作成する

# 4エージェント＋オーケストレーター開発運用

## 1. 目的

この文書は、仕様・テスト・実装・最終レビューの責務を分離し、AIが自らの判断や実装を通すために仕様、テスト、期待結果を調整することを防ぐため、次の4エージェントによる標準運用を定める。

1. 仕様エージェント
2. テストエージェント
3. 実装エージェント
4. レビューエージェント

オーケストレーターは成果物、状態、ゲート、差し戻しを管理する制御役であり、第5の判断エージェントではない。仕様や品質の判断を代行せず、各役割の成果物を直接変更しない。

人間は機能要求、仕様、論理テストケース、中心的契約、最小TDD計画、各承認ゲート、最終的な `Slice Complete` の判断を所有する。

## 2. 適用範囲

原則として、次へ適用する。

- 0→1開発
- 新しいユーザー価値を追加する垂直スライス
- 複数レイヤーや外部境界へ影響する変更
- 仕様と実装の独立した検証が必要な高リスク変更

局所的な文書修正、依存関係更新、単純なリファクタリングなどで分離コストが変更リスクを上回る場合は、適用しない理由、影響範囲、代替する検証方法を変更記録へ残して省略できる。

## 3. 基本原則

### 3.1 論理テストケースを期待動作のsource of truthにする

テストコードは実装から逆算せず、承認済み仕様と論理テストケースから作成する。期待結果を変更する必要がある場合は、先に仕様エージェントへ戻し、人間の再承認を得る。

### 3.2 会話ではなく成果物で引き継ぐ

エージェント間の引き継ぎは、少なくとも次で行う。

- 対象コミットSHA
- 承認済み仕様
- 論理テストケース
- TDD計画
- テスト実行結果
- 実装後テストレポート
- 現在の状態コード
- 未解決事項と差し戻し先

前工程の会話要約だけを根拠にしない。

### 3.3 独立したコンテキストを使う

- 実装エージェントは、テスト作成時の会話コンテキストを引き継がず、リポジトリ上の成果物を読む。
- 実装後テストは、実装エージェントとは独立した新しいテストエージェント実行で行う。
- 最終レビューは、仕様・テスト・実装時の会話コンテキストを引き継がない新しいレビューエージェントで行う。
- 同じ役割を再実行する場合も、前回の主張ではなくコミットと記録を再確認する。

### 3.4 自分で次工程を開始しない

各エージェントは担当工程の結果を返して停止する。次工程への遷移は、オーケストレーターが機械的条件を検査して決める。仕様判断または人間承認が必要な場合は自動遷移しない。

### 3.5 TDDテストを凍結する

`RED_VALIDATED` 後、実装エージェントはTDDテストと期待値を変更しない。変更が必要なら実装を停止し、理由と影響をテストエージェントまたは仕様エージェントへ返す。

### 3.6 自動完了と人間の完了判断を分離する

自動工程の完了は `REVIEW_READY` を意味する。新しいレビューエージェントの統合レビューと、人間の最終判断より前に自動マージしない。

## 4. 役割

| 役割 | 主な責務 | 禁止事項 |
|---|---|---|
| 人間 | 要求提示、仕様・テスト計画・ゲート承認、最終判断 | 判断が必要な事項をAIへ黙示的に委任しない |
| 仕様エージェント | 仕様、論理テストケース、中心的契約候補、最小TDD計画 | テストコード、プロダクトコードを実装しない |
| テストエージェント | TDDテスト、Valid Red確認、実装後テスト、テスト証跡 | プロダクトコードを変更しない。実装へ期待値を合わせない |
| 実装エージェント | 凍結済みTDDテストをGreenにする最小実装とリファクタリング | TDDテスト、仕様、期待値を変更しない |
| レビューエージェント | 新しいコンテキストでの統合レビュー、欠陥分類、差し戻し提案 | 自ら仕様、テスト、実装を修正しない。自己承認しない |
| オーケストレーター | 順序、入力、状態、ゲート、差し戻し、停止の管理 | 仕様・品質判断、成果物の修正、承認の代行をしない |

## 5. 開始条件

人間が「TDD開始」を指示しても、オーケストレーターは次をすべて確認するまでテストコード作成を開始しない。

- Environment Gateが人間に承認済み
- 機能仕様が承認済み
- Blockingの確認事項が0件
- 論理テストケースが承認済み
- 中心的契約が承認済み
- 最小TDD計画が承認済み
- Baselineが記録済み
- 対象ブランチの分岐元SHAが記録済み

不足がある場合は `BLOCKED_SPEC` とし、仕様エージェントと人間へ返す。環境検証に失敗した場合は `ENVIRONMENT_FAILURE` とし、Valid Redへ数えない。

## 6. 標準サイクル

### Stage 0: 仕様作成・承認

仕様エージェントが次を作成または更新し、人間が承認する。

- `docs/specs/<feature-slug>.md`
- `docs/specs/<feature-slug>-test-cases.md`
- `docs/specs/<feature-slug>-tdd-plan.md`

この段階で、目的、対象外、観測可能な振る舞い、受け入れ条件、論理テストケース、中心的契約、最小TDDセット、Baselineを確定する。

### Stage 1: TDDテスト作成

新しいテストエージェントが、承認済み成果物だけを根拠にTDDテストを実装する。

許可される変更:

- テストコード
- テストfixtureとhelper
- テスト実行に必要な最小設定
- Red実行記録

禁止される変更:

- プロダクトコード
- 仕様
- 論理テストケースの期待結果
- 承認済みTDDセットの意味

### Stage 2: Automated Red Gate

オーケストレーターは、次を機械的に確認する。

1. 環境スモークがGreen
2. Baselineに既知でない失敗がない
3. 対象TDDテストが失敗する
4. 失敗理由が承認済み契約の未実装である
5. assertion到達前の環境障害や収集失敗ではない
6. テスト変更にプロダクトコードが混在していない

すべて満たせば `RED_VALIDATED`。環境障害は `ENVIRONMENT_FAILURE`、誤ったテストは `INVALID_RED` または `BLOCKED_TEST` とする。

### Stage 3: 実装

新しい実装エージェントが、対象SHA、承認済み仕様、論理テストケース、TDD計画、凍結済みテスト、Red証跡を読み、テストをGreenにする最小実装を行う。

テスト変更が必要に見える場合は変更せず停止する。

### Stage 4: Automated Green Gate

オーケストレーターは、次を確認する。

1. 対象TDDテストがGreen
2. 影響範囲の回帰テストがGreen
3. lint、format、型チェック、buildの対象項目が完了
4. 凍結済みTDDテストに無断変更がない
5. 仕様外の挙動や無関係な変更がない
6. 実行コマンド、件数、終了コード、SHAが記録されている

通過後は `TDD_GREEN`。失敗時は `IMPLEMENTATION_FAILED` として実装エージェントへ返す。

### Stage 5: 実装後テスト

実装時の会話を引き継がない新しいテストエージェントが、実装済みコードと処理フローを調査し、次を行う。

- 分岐、境界値、例外、状態遷移、レイヤー間接続を分析
- 論理テストケース全体との対応を確認
- 必要な単体、コンポーネント、統合、E2Eテストを追加
- `docs/specs/<feature-slug>-post-test-report.md` を更新
- 全Test Case IDの消化状況と未検証項目を記録

期待動作を仕様から一意に決められない場合は `BLOCKED_SPEC` とし、コードから推測しない。

### Stage 6: Automated Completion Gate

オーケストレーターは、次を確認する。

- 全必須テストと回帰テストがGreen
- 必須の静的検査とbuildが完了
- 全Test Case IDの対応が記録済み
- 未検証項目、Deferred、既知制約が明示済み
- 実装後テストレポートが対象SHAと整合
- 未承認の仕様変更、テスト緩和、範囲外変更がない

通過後は `REVIEW_READY` とする。

### Stage 7: 最終統合レビュー

新しいレビューエージェントが、エージェントの完了報告だけに依存せず、対象差分、仕様、論理テストケース、TDD計画、テスト、実装後テストレポート、CI結果を直接確認する。

レビューエージェントは次を判定する。

- 仕様と実装の整合
- 論理テストケースとテストコードの整合
- Valid RedとGreenの証跡
- 実装後テストの十分性
- セキュリティ、安全性、回帰、運用上の懸念
- 範囲外変更と未解決事項
- 欠陥の分類と戻り先

問題がなければ人間へ最終判断を依頼する。問題があれば自ら修正せず、該当工程へ差し戻す。

### Stage 8: 人間の完了判断

人間がレビュー結果と証跡を確認し、`Slice Complete`、差し戻し、またはDeferredを判断する。マージはこの判断後に行う。

## 7. 差し戻し規則

| 発見した問題 | 戻り先 | 再実行する範囲 |
|---|---|---|
| 要求、仕様、受け入れ条件、期待結果の不足・矛盾 | 仕様エージェント | 影響する仕様・論理テストケースを再承認し、Red Gate以降を再実行 |
| テストの誤り、不足、過剰制約 | テストエージェント | テスト修正後、Red Gate以降を再実行 |
| 実装が承認済み仕様・テストを満たさない | 実装エージェント | Green Gate以降を再実行 |
| テスト容易性のためプロダクト境界変更が必要 | 仕様エージェントと人間 | 変更を承認後、影響する最も早い工程から再実行 |
| テスト環境、依存取得、起動、fixtureの失敗 | テスト環境整備 | 同じ工程を再開。Valid Redや実装欠陥に数えない |
| 最終レビューで複数分類にまたがる問題 | オーケストレーターが最も早い該当工程へ戻す | 下流のGateと証跡をすべて更新 |

上流成果物を変更した場合、その成果物に依存する下流の承認とGateは自動的に有効とはみなさない。

## 8. 状態コード

| 状態 | 意味 |
|---|---|
| `READY` | 開始条件を満たした |
| `SPECIFYING` | 仕様エージェントが作業中 |
| `TESTING_RED` | TDDテスト作成中 |
| `RED_VALIDATED` | Automated Red Gate通過 |
| `IMPLEMENTING` | 実装中 |
| `TDD_GREEN` | Automated Green Gate通過 |
| `POST_TESTING` | 独立した実装後テスト中 |
| `REVIEW_READY` | Completion Gate通過、最終レビュー待ち |
| `REVIEWING` | 独立した最終レビュー中 |
| `SLICE_COMPLETE` | 人間が完了を承認 |
| `BLOCKED_SPEC` | 仕様または期待動作の判断待ち |
| `BLOCKED_TEST` | テスト設計またはテスト実装の修正待ち |
| `BLOCKED_TESTABILITY` | テスト容易性に関する設計判断待ち |
| `INVALID_RED` | 失敗理由が承認済み契約の未実装ではない |
| `IMPLEMENTATION_FAILED` | 実装またはGreen Gateが失敗 |
| `ENVIRONMENT_FAILURE` | 環境障害。Valid Redではない |
| `REVIEW_FAILED` | 最終レビューで差し戻しが必要 |

## 9. 変更境界

| 役割 | 仕様・論理ケース | テストコード | プロダクトコード | 実行記録・レポート |
|---|---:|---:|---:|---:|
| 仕様エージェント | 作成・更新 | 変更しない | 変更しない | TDD計画を更新 |
| テストエージェント | 変更しない | 作成・更新 | 変更しない | Red証跡・実装後レポートを更新 |
| 実装エージェント | 変更しない | 変更しない | 作成・更新 | Green証跡を追記 |
| レビューエージェント | 変更しない | 変更しない | 変更しない | レビュー結果を記録 |
| オーケストレーター | 変更しない | 変更しない | 変更しない | 状態とGate結果を記録 |

例外的な変更が必要な場合は作業を継続せず、理由、必要な変更、影響するGateを記録して該当役割へ返す。

## 10. コミットと証跡

推奨する論理コミット境界は次のとおり。

1. 仕様・論理テストケース・TDD計画
2. TDDテストとValid Red証跡
3. プロダクト実装とTDD Green証跡
4. 実装後テストとレポート
5. レビュー指摘に対する役割別の修正

最低限、各Gateに対象SHA、実行コマンド、結果、終了コード、件数、既知の例外を残す。

## 11. 最終レビューのチェック項目

レビューエージェントは少なくとも次を確認する。

- 仕様のBlocking項目が0件
- 人間承認済みの成果物と対象SHAが明確
- TDDテストが論理テストケースへ追跡可能
- Valid Redが環境障害やテスト誤りではない
- 実装エージェントが凍結済みTDDテストを変更していない
- 実装が仕様外の挙動を追加していない
- 実装後テストが分岐、境界、例外、接続を検討している
- 全Test Case IDの結果またはDeferred理由がある
- lint、型チェック、単体、統合、E2E、buildの必要項目が完了
- 残余リスクと既知制約が明示されている
- 差し戻しが必要な場合、問題分類と戻り先が明確

## 12. Skillsとの関係

この文書は開発サイクルの契約である。各工程を実行するSkillsは、この契約に従って別途整備する。

Skillsは明示的に呼び出した場合だけ開始し、少なくとも次を満たす。

- 担当役割と変更可能範囲を宣言する
- 必要な入力成果物と承認状態を検査する
- 対象SHAと状態コードを記録する
- 担当外の問題を修正せず、定義済みの戻り先へ返す
- 次工程を無断で起動または承認しない

テスト環境の構築・検証には既存の `setup-test-environment` Skillを使用する。これは開発サイクルの各実行Skillとは独立し、機能TDDや実装を開始しない。
